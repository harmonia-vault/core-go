# 恢复来源设备与第四版 CLI 入网

这是实验性实现，不能宣称生产可用。

## 固定本机信任来源

`NewRecoveredDevicePinnedVerifier` 接收已验证并受保护保存的原根 pin、原始双签初始化、完整恢复轮换链和明确选择环境权限的恢复设备双签原包。`cryptox.BuildRecoveredDeviceIssuerEvidence` 负责从这些原材料构造第一条显式 `recovered` 身份边；它不会移动原根，也不赋予当前在线会话或全局管理者身份。

构造器逐项绑定账号及代际、本机独立 Ed25519/X25519 双公钥、原包摘要及接受序号、明确选择的自身环境授权。之后仍需持钥 `BootDevice`、正常逐环境验证 `Pull` 和最终本机加密保存，手机控制器才能开放可信管理。服务端目录不能建立或替换这些本机材料。

## 明确版本与能力

CLI 保持默认第三版；恢复来源管理手机需要用户明确指定 `pair --certificate-version 4`。第四版使用独立 `/pairings-v4` 及单一 `issuer-recovery-v1` 能力。成熟原生 SPAKE2 双向确认后，管理者签完整来源证明，申请设备验证所有授权与 HPKE 封套并双签证书。短码及 PAKE 临时私钥不进入 HTTP 或持久状态。默认无原生 SPAKE2 的构建仍关闭新配对。

保存的原始双签回执不可换版本、名单或证明。丢失提交响应后仅查询并幂等重试这一原回执，不另造短码、密钥或授权。后台恢复验签与当前权限校验相互独立，历史挑战期限不会复活当前已到期授权。

`pull?capability=issuer-recovery-v1` 的 `issuerEvidence` 字段使用明确的第三版来源图。旧能力的解析器仍严格拒绝此图；新能力也拒绝旧图、缺失初始化、缺失恢复链或恢复链头回退。完整图验证使用原受保护 pin，并要求保留已见恢复链头及其接受序号。所有初始化、恢复轮换及恢复设备接受序号必须不大于本次持久检查点。

## 数据与授权账本

完整已验证的来源账本与快照一起原子保存于加密 `state-v1`；写入失败不能先在内存推进。正式第四版缓存必须带账本及每环境已验数据来源，不自动迁移明文或旧能力缓存。

普通下发继续复用现有签变更、完整批次、当前授权、已见变更序号及逐环境解密校验。暂停时只处理授权投影：当前授权和来源账本可以前进，数据序号和已见普通变更不前进，旧数据的来源 KV/GG 保留。降权、到期、撤销及删除仍执行；升级不提前作用于旧数据。恢复同步后通过完整下发重建当前数据。

客户端通知只唤醒相同 `Pull`，不直接写账本。共享写入仍在线、按服务器接受顺序 LWW，只有成功的同一验证下发才能更新本机。第四版现有 CLI 变量写入复用原密封幂等日志，没有另设乐观缓存更新。

## 当前验证边界

固定合成密钥的密码学、来源账本、本机公钥、原证书版本、接受序号下界及缓存权限负例已实际运行。Go 同步、原生状态存储和 CLI 普通测试与 race 已通过，三平台默认纯 Go 构建已通过。默认构建中的原生配对验收需要显式原生 tag，缺原生库应标记未跑或跳过。

`workspace/acceptance/recovery_cli_v4_test.go` 已使用真实 TypeScript/SQLite HTTPS 服务与手机高层恢复流程，完成原恢复码到重输新码的连续轮换、恢复管理设备明确登记、原生 BoringSSL SPAKE2 批准真正编译的第四版 CLI。丢失双签提交响应后，新进程用原密封回执查询接受结果，未重发新入网请求。随后关闭配对进程，以普通 CGO0 CLI 启动后台，实际执行新持钥启动与 HPKE 解密下发；只读设备拒写，可写设备通过唯一后台 IPC 在线写入和删除，经同一验证下发更新本机。该定向联合测试普通执行通过（8.34 秒），race 执行通过（10.11 秒）。测试只使用合成账号、凭据、环境值和短路径临时目录；没有安装宿主系统服务或采集宿主环境。

第四版环境生命周期及现有设备权限管理仍依赖旧的第二版来源控制接口；当前新能力严格拒绝其图，尚未接入兼容新恢复来源的明确控制联合类型，不能把本次变量读写闭环视为这些管理功能全部完成。Windows 专用服务身份、DPAPI 与用户 profile 的原生运行门槛仍保留。
